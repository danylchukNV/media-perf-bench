## Що це за проєкт

Тестовий стенд для **дипломної роботи** на тему:
**«Розробка та дослідження методу оптимізації продуктивності вебзастосунків із високоінтенсивним мультимедійним контентом»**.

Запропонований метод — **АКПМ** (адаптивна контекстно-залежна пріоритизація завантаження медіаресурсів). Ідея: принципи адаптивного бітрейту з відео поширюються на всі медіа сторінки. Кожен ресурс має пріоритет і «дедлайн», тобто прогнозований момент, коли він з'явиться у вікні перегляду. Метод обирає найвищу якість, яку встигне завантажити до цього моменту.

- **Формула (1), пріоритет:** `P = wv·V + ws·S + wt·T − wc·C`
  - V — близькість до вікна перегляду;
  - S — семантична важливість;
  - T — імовірність появи у вікні за горизонт прогнозу (з урахуванням швидкості прокручування);
  - C — вартість завантаження.
- **Формула (2), вибір якості:** `q* = max { q : size(q)/B ≤ τ }`. B — оцінка пропускної здатності, τ — час до появи елемента.

## Структура коду

Детально — у `README.md`.
- `src/akpm/*.ts` — бібліотека методу. Модулі відповідають компонентам з тези 2: context (1), priority (2), quality (3), index (4–5: планувальник, рендеринг), video, feedback (6).
- `scripts/generate-media.mjs` — медіа та `manifest.json`; `scripts/build-pages.mjs` — сторінки `/a`, `/b`, `/b2`, `/c`.
- `bench/run.mjs` — раннер Puppeteer; `bench/probe.js` — вимірювальний зонд; `bench/analyze.mjs` — статистика (медіана, p75, U-критерій Манна — Уїтні).
- Усі параметри експерименту — у `bench.config.mjs`.

Команди: `npm run media`, `npm run build`, `npm run serve`, `npm run bench -- --runs 3 --networks slow4g --devices mobile`, `npm run analyze`, `npm run typecheck`.

## Рішення, вже ухвалені (не змінювати без обговорення)

- Банер (головне зображення) у конфігурації В завантажується так само, як у Б (`<picture>` + `fetchpriority="high"`). Бібліотека керує рештою медіа і на час завантаження банера пропускає лише видимі елементи (`heroGateMs`).
- hls.js у В підвантажується ліниво, лише коли відео наближається до вікна; у Б підключається через `defer`.
- Конфігурацій чотири: А, Б, **Б′** (`/b2`, Б + `capLevelToPlayerSize: true` для hls.js) і В. Аналіз порівнює В і з Б, і з Б′ (рішення 18.11.2026).
- У В рівень відео обмежений розміром плеєра явно (`autoLevelCapping` після `MANIFEST_PARSED`), бо власне `capLevelToPlayerSize` hls.js не скрізь отримує розмір плеєра.
- Профілі для тези: `slow4g × mobile` (основна таблиця) і `fast4g × desktop`, по 20 прогонів.
- Скасування запитів має гістерезис: запуск у межах 1,5 екрана, скасування далі 2,5 екрана, після скасування пауза 1 с.
- Трафік рахується через події DevTools Protocol, включно зі скасованими запитами.
- LCP у А часто дорівнює тексту, бо банер не встигає відобразитися. Тому в аналізі є окремі рядки: «Час відображення головного зображення» (Element Timing, `elementtiming="hero"`) і «LCP-елемент — зображення».
- `content-visibility` у В вимкнено за замовчуванням (прапорець `--cv` у build-pages), бо може впливати на CLS.
- TBT рахується за всю сесію, включно з прокручуванням. Це не те саме, що TBT у Lighthouse, і в тезі це треба оговорити.
