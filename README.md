# Тестовий стенд: метод АКПМ

Стенд для експериментальної тези «Експериментальне дослідження ефективності методу адаптивної контекстно-залежної пріоритизації завантаження медіаресурсів».

Вміст однаковий у трьох конфігураціях, стратегії завантаження різні:

| Конфігурація | URL | Що всередині |
|---|---|---|
| **А** — базова | `/a` | `orig.jpg` (~2400 px, JPEG q90) без `width/height`, усі зображення одразу; відео — `mp4` 1080p з `autoplay preload="auto"` |
| **Б** — стандартні практики | `/b` | `<picture>` AVIF/WebP/JPEG + `srcset/sizes`, `loading="lazy"`, `decoding="async"`, `fetchpriority="high"` для банера; відео — HLS (hls.js з ABR за замовчуванням), підключається при 50% видимості |
| **В** — метод АКПМ | `/c` | банер — як у Б; решта медіа — бібліотека `src/akpm` (пріоритет, вибір якості за дедлайном, планувальник, скасування запитів, керування відео, зворотний зв'язок) |

## Встановлення

Потрібно: **Node.js 20+**, **ffmpeg** (для відео; без нього стенд працює без відео).

```bash
npm install            # Puppeteer сам завантажить Chrome for Testing
npm run media          # генерує медіа (~10 хв: AVIF кодується повільно)
npm run build          # збирає бібліотеку АКПМ і три сторінки
npm run serve          # http://localhost:8080/a, /b, /c — переглянути вручну
```

**Рекомендовано: власні фото й відео.** Покладіть 40–80 фото в `media-source/images/` і 3–6 відео в `media-source/videos/`, потім повторіть `npm run media && npm run build`. Синтетичні медіа підібрані так, щоб розміри файлів були близькими до реальних фото (1920 px: JPEG ≈ 400 КБ, AVIF ≈ 200 КБ). Але для тези переконливіші реальні знімки, бо від вмісту залежить, наскільки добре стискається кожен формат. Беріть власні фото або фото з вільною ліцензією і вкажіть джерело в роботі.

## Експеримент

```bash
npm run bench                                          # повний план із bench.config.mjs
npm run bench -- --runs 3 --networks slow4g --devices mobile   # швидка перевірка
npm run analyze                                        # таблиці → results/summary.md, summary.csv
```

Повний план за замовчуванням: 3 конфігурації × 3 мережі × 2 пристрої × 20 прогонів = 360 прогонів, по 30–60 с кожен (**4–6 годин**). Його можна розбити на частини:

```bash
npm run bench -- --networks slow4g --devices mobile    # основна таблиця для тези (~1 год)
npm run bench -- --networks fast4g --devices desktop
npm run analyze -- results/raw-*.jsonl                 # об'єднати всі файли
```

Під час прогонів не навантажуйте комп'ютер: емуляція уповільнення CPU відносна, тож фонові задачі спотворюють INP і TBT. Ноутбук тримайте на живленні.

### Що робить один прогін

1. Новий профіль браузера (як режим інкогніто), кеш вимкнено, сервер віддає `Cache-Control: no-store`, тобто кожен прогін «холодний».
2. Емуляція мережі (DevTools Protocol) і пристрою: мобільний 412×915, DPR 2,625, CPU ×4; настільний 1366×768.
3. Відкриття сторінки, очікування `load` (не довше 20 с), пауза 2 с.
4. Прокручування 9000 px зі швидкістю 900 px/с, паузи по 1,2 с кожні 1800 px, зупинка на 4 с на кожному відео (перегляд), 3 кліки «лайк» (для INP).
5. Ще 3 с очікування, збір метрик.

Порядок конфігурацій перемішується в кожному раунді, щоб уникнути систематичного зсуву.

### Метрики

| Метрика | Як вимірюється |
|---|---|
| LCP, CLS, INP, FCP, TTFB | бібліотека `web-vitals` 4.x, вставляється в сторінку раннером |
| TBT | Σ(тривалість − 50 мс) довгих задач після FCP **за всю сесію**, включно з прокручуванням. Це не лабораторний TBT Lighthouse (той рахується лише до TTI), тому в тезі варто вказати визначення |
| Обсяг даних, кількість запитів | події DevTools Protocol, включно зі скасованими запитами (чесно для методу, який скасовує запити) |
| Час до старту відео | від моменту, коли відео видно на ≥ 50%, до першої події `playing`; медіана по відео в прогоні |
| Зупинки відео | події `waiting` після початку відтворення |

Статистика (`bench/analyze.mjs`): медіана, 75-й процентиль, зміна В відносно Б у %, двосторонній U-критерій Манна — Уїтні (нормальне наближення з поправками на зв'язки), α = 0,05.

Обсяг даних у конфігурації А на повільних мережах обмежений тривалістю сесії: сторінка просто не встигає все завантажити. Це нормально і варто згадати в тезі.

### Lighthouse CI (додатково)

```bash
npm run serve &        # в окремому терміналі
npm run lhci           # 3 прогони кожної сторінки, симуляція Slow 4G, звіт у .lighthouseci/
```

Lighthouse вимірює лише завантаження без прокручування, тому основні дані дає `npm run bench`.

## Параметри

Усе налаштовується в `bench.config.mjs`: кількість медіа, ширини, якість кодування, мережеві профілі, пристрої, сценарій, кількість прогонів.

Параметри методу (у `scripts/build-pages.mjs` → `AKPM.init({...})`):

| Параметр | За замовч. | Значення |
|---|---|---|
| `weights` | `{v:0.4, s:0.3, t:0.3, c:0.2}` | ваги формули (1): P = wv·V + ws·S + wt·T − wc·C |
| `horizonMs` | 3000 | горизонт прогнозування (коригується зворотним зв'язком у межах 1,5–6 с) |
| `visibleBudgetMs` | 1500 | бюджет часу τ для вже видимого елемента у формулі (2) |
| `heroGateMs` | 2500 | скільки чекати на головне зображення, перш ніж вантажити інше |
| `dprCap` | 2 | максимальний DPR при виборі роздільності |
| `persist` | true | зберігати оцінку мережі й горизонту між відвідуваннями (у бенчмарку кожен прогін новий, тож не впливає) |
| `debug` | false | журнал рішень у консолі |

`node scripts/build-pages.mjs --cv` вмикає `content-visibility: auto` для карток у конфігурації В. За замовчуванням вимкнено, бо може впливати на CLS; перевіряйте окремо.

Під час перегляду `/c` у консолі `AKPM_STATS` показує, що робила бібліотека: завантаження, покращення якості, скасування, промахи, оцінку мережі, горизонт.

## Структура

```
bench.config.mjs           конфігурація експерименту
scripts/generate-media.mjs медіа + manifest.json
scripts/build-pages.mjs    сторінки A/B/C
src/akpm/                  бібліотека методу (TypeScript)
  context.ts               компонент 1 — мережа, пристрій, прокручування
  priority.ts              компонент 2 — модель пріоритету, формула (1)
  quality.ts               компонент 3 — вибір якості, формула (2)
  index.ts                 компоненти 4–5 — планувальник, рендеринг
  video.ts                 керування відео (HLS, старт-рівень, пауза/зупинка)
  feedback.ts              компонент 6 — зворотний зв'язок
server.mjs                 статичний сервер (no-store, Range)
bench/probe.js             вимірювальний зонд у сторінці
bench/run.mjs              раннер (Puppeteer)
bench/analyze.mjs          статистика і таблиці
```

## Відомі обмеження

- Емуляція мережі DevTools додає затримку до кожного запиту і не моделює втрати пакетів. Для перевірки на реальних мережах запустіть сервер на іншій машині або в хмарі.
- Сервер працює через HTTP/1.1 (Chrome відкриває до 6 з'єднань на хост). Через CDN з HTTP/2 і HTTP/3 абсолютні значення будуть іншими, а порівняння конфігурацій лишається коректним, бо умови для всіх однакові.
- Анімовані прев'ю в стенді реалізовані як короткі зациклені відео (сучасна практика замість GIF).
